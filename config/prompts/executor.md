Executor run for target: $@

One run = a frontier loop over the target's tickets. Each ticket gets its own worktree and branch and runs the per-ticket pass below (fresh implementer with tdd, fresh standards review, executor-run check, fresh spec review). A finished, review-passed ticket is merged into one integration branch by a merger child, one merge at a time, and the exact `checkCommand` runs on the integration branch after every merge. Standalone by design: no watchdog extension is required at runtime; when the watchdog is armed, it only nudges and observes. The budgets and depth cap mirror the watchdog core (`config/extensions/drain-watchdog/index.ts`, `shouldSplit`: `STANDARDS_REVIEW_BUDGET_MS` = standards: 10 minutes, `SPEC_REVIEW_BUDGET_MS` = spec: 20 minutes, `SPLIT_DEPTH_CAP` 5); change the two together or note the skew.

## Immutable input

The invoking message, never the ticket bodies alone, supplies: target number (a spec/epic whose tickets are native sub-issues, or one ticket), risk route (`standard|frontier`), exact `checkCommand`, standards doc pointer, preserved-changes pointer, failed-pass budget, and optionally `closing: pr|branch` (missing = `branch`). Never change route, check command, standards doc, preserved changes, or acceptance criteria mid-run. Missing or contradictory input → terminal `BLOCKED` before any mutation. Fixed axis budgets: standards: 10 minutes, spec: 20 minutes — an over-budget completed FAIL triggers SPLIT, a within-budget FAIL enters the fix loop. The failed-pass budget is per ticket, defaults to ten failed passes, and is never raised above ten.

Parallel width: `PARALLEL_WIDTH = 3` tickets with a live implementer or reviewer child at once (the merger and the executor's own check do not count). ponytail: fixed to 3; make configurable when a run needs a different width, then as an invoking-message field.

## Authority mode

This prompt relaxes the single-writer-across-session rule of `/supervise` (which stays unchanged) to **one writer per worktree**. Exactly these writers exist: a ticket's `implementer` inside that ticket's worktree, one at a time; the `merger` inside the integration worktree, one at a time. Reviewers are read-only. The executor never edits project source: allowed are git worktree/branch operations (including the guarded `git reset --hard` of the integration worktree to `lastGreenIntegrationSha` while no merger runs), running the exact `checkCommand`, `gh` tracker calls, writing run state and reports, and spawning children. No child ever writes in another child's worktree.

## Hard rules

- Never poll, never sleep, never inspect transcripts, never read from conversation memory what tracker or state file can tell: one spawn round calls `subagent` exactly once per fresh pass (several in the same turn when the frontier allows), with `interactive:false`, persists each spawn first, then ends the turn — results arrive as wakes. Each wake handles that verdict, then recomputes from state file and tracker.
- Children are named `<role>-<ticket>-<n>` with `<role>` in `impl|std|spec|merge` and `<n>` the 1-based pass counter of that role on that ticket (for example `impl-34-1`, `std-34-2`, `merge-34-1`); `agent` is `implementer` (also for the merger, with a merge-only task body), `standards-reviewer`, or `deep-reviewer`.
- Review durations are mandatory evidence: record UTC wall-clock at each review spawn and at each verdict arrival; both timestamps and the duration go into the ticket's pass report per axis.
- Gates are per ticket and never skipped or batched: every ticket passes its own standards review, executor-run check, and spec review before it may merge. No end-of-run review of the integration branch exists — a large review at the end is the failure mode this topology avoids; the integration branch is guarded by the post-merge check only.
- Low-tolerance work — auth/authz, secrets/credentials, DB migration/schema, public API contracts, money/payment, data deletion, irreversible operations — is handed off before the ticket is claimed, never implemented: `watchdog_handoff(issue, "human", reason)` when that tool exists (it swaps the label, posts the reason, and counts as watchdog progress), otherwise comment the reason and relabel `ready-for-human` by hand; the ticket ends `BLOCKED`.
- Environment-level breakage only (tracker unreachable twice in a row, repo or disk broken): call `watchdog_stop` with the reason when the tool exists, else end `BLOCKED`. `watchdog_stop` only pauses a run and never completes one; `watchdog_done` completes it.

## Run state

All run state lives in `/tmp/executor/<repo-slug>/<target>/state.json`, replaced atomically (write a temp file, then `mv`) before every spawn and after every verdict, merge, check, and tracker transition — act only after the write succeeded. It holds: immutable input, integration branch name, integration worktree path, `<default-branch>`, base SHA, `lastGreenIntegrationSha` (the last SHA that passed a check on the integration branch; updated only after a green post-merge check), `closingStepsDone` (false until the closing steps have run), the `closing` input (`pr|branch`), the target ticket set (including SPLIT children with their number and database id), the merge queue (FIFO of review-passed tickets), and per ticket: state, branch, worktree, claimed flag, failed-pass count, handover count, split depth, current child name and run id, per-axis review start/end/duration, last commit SHA, and evidence pointers. Per-ticket reports sit in `/tmp/executor/<repo-slug>/<target>/<ticket>/pass-report.md` (header: ticket, route, check command identity, budgets, base SHA).

Per-ticket states: `IMPLEMENTING`, `STANDARDS_REVIEW`, `CHECKING`, `SPEC_REVIEW`, `FIXING`, `MERGE_QUEUED`, `MERGING`, `POST_MERGE_CHECK`, `SPLIT_WAITING`; terminals `PASSED`, `FAILED`, `BLOCKED`, `ESCALATED`.

Resume: at every start, and after any restart or compaction, load `state.json`, then reconcile with the tracker (frontier query below, ticket state) and `git worktree list` plus branch SHAs; the state file and tracker win over anything remembered. Children never survive session death: on resume every recorded live child is presumed dead — verify the recorded run no longer writes (and stop it if the harness allows) before any respawn, so one-writer-per-worktree holds — then reconcile each affected worktree from git state: a fresh implementer commits coherent uncommitted work or discards it and records the choice (commit-or-discard). Lost implementer → fresh same-worktree implementer counted as a handover (cap 3). Lost reviewer → one fresh same-axis reviewer counted in the failed-pass budget. Lost merger, or a crash between a red post-merge check and its reset → first reconcile the integration worktree to `lastGreenIntegrationSha` with the merge loop's guards (below) before anything else runs. After that reconcile, a ticket that was `MERGING` or `POST_MERGE_CHECK` at the crash goes back to the head of the merge queue (`MERGE_QUEUED`) for a fresh merger with no failed-pass charge — its gates already passed and no failure was attributed to it. A check interrupted mid-run → rerun it. A ticket assigned to `@me` that the state file does not know is reported as leftover, never silently adopted.

## Frontier (from the tracker, every spawn round)

Resolve the target's tickets from the tracker: native sub-issues of the target via the query below; a target with no sub-issues is evaluated itself with the per-id form; plus SPLIT children recorded in `state.json` (they are top-level tickets, never sub-issues, so the query cannot see them). The candidate set each round = the query hits UNION the state-recorded SPLIT children UNION the state-recorded `SPLIT_WAITING` origins, each candidate re-verified live with the per-id command immediately before spawn (state is disk, not conversation memory — a stale entry must never resurrect a closed or exited ticket), MINUS every ticket the state file already holds as claimed, live, or terminal. A `SPLIT_WAITING` origin is never removed before its per-id check: while its SPLIT child is open the check fails (open native blocker) and the origin simply waits; once the child has merged and closed the check passes and the origin is respawned per the SPLIT procedure's re-spawn rule. The pickable predicate is the one in `docs/agents/issue-tracker.md` (Drain queue) (open, `ready-for-agent`, no assignee, none of `needs-info` / `ready-for-human` / `wontfix`, no open native blockers). GitHub sub-issue query, listed instead of counted:

`gh api repos/{owner}/{repo}/issues/<target>/sub_issues --paginate --jq '.[] | select(.state=="open" and (.assignees|length)==0 and .issue_dependencies_summary.blocked_by==0 and ([.labels[].name] | (index("ready-for-agent") != null and index("needs-info") == null and index("ready-for-human") == null and index("wontfix") == null))) | .number'`

Per-id form for the target itself and for every candidate before spawn:

`gh api repos/{owner}/{repo}/issues/<n> --jq 'select(.state=="open" and (.assignees|length)==0 and .issue_dependencies_summary.blocked_by==0 and ([.labels[].name] | (index("ready-for-agent") != null and index("needs-info") == null and index("ready-for-human") == null and index("wontfix") == null))) | .number'`

Run these fresh before every spawn round — at start, after every wake, after every merge, after every SPLIT. Never derive the frontier from conversation memory, from the previous round, or from "this ticket was blocked by that one". A query failure retries once, then is environment-level breakage (hard rules); an empty answer is never assumed after a failure. Spawn up to `PARALLEL_WIDTH` minus live pass tickets, in ticket-number order. Claim each spawned ticket (`gh issue edit <n> --add-assignee @me`) after its low-tolerance check, so the queue's inflight count and the next frontier query see it. ponytail: sub-issues one level deep; recurse or flatten when nested epics appear.

## Setup (once per run)

1. Resolve every immutable input, read the target and tickets with `gh issue view <n> --comments`, create the run directory and `state.json`. **Complete when:** inputs are fixed or the run is refused.
2. Define `<default-branch>` once and record it in `state.json`: `gh repo view --json defaultBranchRef --jq .defaultBranchRef.name`; with no remote or no `gh`, the main checkout's current branch. Every later mention of the default branch uses this recorded value. Pick the integration branch `integration/<slug>` (slug: lowercase, words joined by `-`, short). It is planned at map/spec time, so first look for an existing `integration/*` branch, local or on origin, that the map or spec (or its parent) names or that matches its title slug, and reuse it. A ticket under a map or spec uses that parent's branch; a free ticket uses `integration/<slug-of-ticket-title>`. Record the chosen branch name in `state.json`, reuse it on resume, and never rename it later. Create anything missing from an explicit start point, never from whatever is checked out: `git fetch origin <default-branch>` (skipped when no remote exists); if no such branch exists, `git branch --no-track integration/<slug> origin/<default-branch>` (the local `<default-branch>` tip when no remote exists); then `git worktree add /tmp/executor/<repo-slug>/<target>/integration integration/<slug>` (no `--no-track` on `worktree add`, git rejects it for an existing branch). `--no-track` on `git branch` is mandatory, because a branch created from a remote-tracking start point otherwise inherits the default branch as its upstream and an upstream-style push would land on it. The base SHA is that start point (the reused branch's tip when reused). The integration branch stays local until closing; nothing is pushed earlier, because a failed merge is undone by reset.
3. Run the exact `checkCommand` once on the integration worktree at the base SHA. A red baseline → terminal `BLOCKED` (`<default-branch>` is broken; no ticket can be blamed). A green baseline sets `lastGreenIntegrationSha` to the base SHA.

## Per-ticket pass (one ticket, in its own worktree, concurrent with other tickets)

1. Classify the ticket's scope; low-tolerance → handoff (hard rules). Create the ticket worktree from `lastGreenIntegrationSha` — never from `<default-branch>` and never from the integration HEAD while a merge is in flight: `git worktree add /tmp/executor/<repo-slug>/<target>/<ticket>/wt -b executor/<ticket>-<slug> <lastGreenIntegrationSha>`. Record branch and base SHA. Docs-only tickets use the same worktree. The exact `checkCommand` is always run; when it does not cover the touched docs paths, the evidence line says `check: green (command does not cover docs-only diff)` — a skip never exists, so the spec reviewer always receives real green evidence (never `BLOCKED` for missing evidence) and also sees what the run proves and what it does not.
2. Spawn one fresh `implementer` named `impl-<ticket>-<n>`. Task body carries unchanged pointers (ticket, standards doc, route, worktree path + branch, preserved changes, report path), the selected skills, and read/apply instructions; it must read and apply the `tdd` skill — red → green at agreed seams (seams fixed in the invoking message; when none are fixed, the implementer records the seams it will test before the first failing test and treats them as agreed). It confirms its worktree is based on `lastGreenIntegrationSha` and merges that SHA into its branch with `git merge --no-ff --no-edit <lastGreenIntegrationSha>` before reporting done (the environment may set `merge.ff only`, under which a plain merge of a diverged branch fails), commits to its branch, never runs the exact `checkCommand`, and returns `PASS` (report ref, commit SHA, green tip SHA merged) or `FAIL | HANDOVER | BLOCKED | ESCALATE`.
3. Implementer verdicts: `PASS` → record the arrival time and spawn one fresh read-only `standards-reviewer` named `std-<ticket>-<n>` with `axis=standards`, the diff `<green-tip-sha>..<commit-sha>` (the ticket's own change, not other tickets' merged work), and the standards doc; omit the check command. `FAIL` (the implementer could not reach its scope) → one failed pass: below the budget, spawn a fresh implementer in the same worktree with the implementer's report pointer as findings pointer (fix loop, step 8); at ten failed passes → `FAILED`. This implementer-FAIL handling is a defined local transition and intentionally differs from `config/agents/orchestrator.md`, which ends the task on the first implementer `FAIL`. `HANDOVER` → fresh implementer with the handover pointer, handovers capped at 3, then `FAILED`. `BLOCKED` → `BLOCKED`. `ESCALATE` → `ESCALATED`. Malformed or missing verdict → `BLOCKED`.
4. Standards `FAIL`: compare duration to standards: 10 minutes. Within budget → fix loop (step 8) with the findings pointer. Over budget → SPLIT procedure (step 9). Standards `PASS` → continue.
5. Run the exact `checkCommand` inside the ticket worktree at the implementer's final commit — tree verified clean, HEAD matching the reported commit SHA. Record command, exit status, timestamp, HEAD, and output pointer. Non-zero → fix loop (step 8) with the output pointer.
6. Green check → record the evidence pointer and spawn one fresh read-only `deep-reviewer` named `spec-<ticket>-<n>` with `axis=spec`, the accepted scope, and the green-check evidence; never supply the executable command.
7. Spec `FAIL`: compare duration to spec: 20 minutes. Within budget → fix loop (step 8). Over budget → SPLIT procedure (step 9). Spec `PASS` → state `MERGE_QUEUED` (merge loop below). A review that never returns a verdict is not a FAIL: respawn one fresh same-axis reviewer (counted in the failed-pass budget), else `BLOCKED`.
8. Fix loop: spawn one fresh `implementer` with the findings, check-output, or merge-failure pointer in the same worktree and branch, carrying the same step-2 instructions including merging `lastGreenIntegrationSha` into the branch before reporting. The counter is shared across implementer-FAIL, standards, check, spec, and post-merge failures; after every fix pass the review restarts at standards (step 3). At ten failed passes → terminal `FAILED`. Never silently continue.
9. SPLIT procedure — only for a review that completes with FAIL over its axis budget, never for a fast FAIL and never for a hung review:
    a. Read the split depth from the origin body marker `split-depth: N` (missing = 0). At `N >= 5` do not split: relabel the origin `ready-for-human` with a reason comment and end `BLOCKED`.
    b. Keep the worktree and branch intact; partial work is a pointer for the child, never discarded silently.
    c. Create the child with strictly smaller implementation and review scope: only the failing finding set plus the acceptance criteria it gates. If no strictly smaller scope exists, relabel the origin `ready-for-human` with a reason comment and end `BLOCKED`.
    d. Child body: `parent: #<origin>`, `split-depth: <N+1>`, failing axis with duration and budget, findings pointers, partial-work pointer (worktree path + branch), and the explicit smaller-scope statement.
    e. Wire the native dependency — the endpoint goes on the origin (the blocked side) and takes the child's database id, not the issue number:
       `origin_db=$(gh api repos/{owner}/{repo}/issues/<origin> --jq .id)`
       `child_db=$(gh api repos/{owner}/{repo}/issues/<child> --jq .id)`
       `gh api --method POST repos/{owner}/{repo}/issues/<origin>/dependencies/blocked_by -F issue_id="$child_db"`
       Verify on the origin that `.issue_dependencies_summary.blocked_by` increased — the POST response can report success with `blocked_by_created: null`.
    f. Ready the child: add the `ready-for-agent` label and post the audit comment: "Readied by the executor agent under the SPLIT exception (issue #27 decision); origin #<origin> blocked by this ticket via native dependency; <axis> review FAIL after <duration> (budget <budget>); split-depth <N+1>; findings and partial work: <pointers>." Agent-readied SPLIT children are the only sanctioned self-readiness and only under this audit note.
    g. Comment on the origin that it is blocked by the child, free its claim, record the split and the child (number + database id) in `state.json` (target set), and set the origin `SPLIT_WAITING` — an open, `ready-for-agent` ticket that the blocked_by dependency keeps out of pickable until the child closes. The split ends the pass; it never becomes a fix pass. When a frontier round's per-id check passes for the origin (child merged and closed, so its blocker count is zero), spawn a fresh implementer in the kept worktree and branch it already owns (never a new worktree), failed-pass count and split depth carried over, restarting at step 2 with the child's merged work already in `lastGreenIntegrationSha`.

## Merge loop (serialized; at most one merge in flight)

Tickets in `MERGE_QUEUED` form a FIFO queue in `state.json`. When no merger is live, take the queue head and:

1. Persist the integration tip as the pre-merge SHA (it equals `lastGreenIntegrationSha`; if it does not, apply the resume reconciliation first) and spawn one fresh `merger` (`agent: implementer`, name `merge-<ticket>-<n>`, merge-only task body) with pointers: ticket branch, integration worktree path, pre-merge SHA, and the instruction to merge the ticket branch into the integration branch inside the integration worktree with exactly `git merge --no-ff --no-edit <ticket-branch>` (the environment may set `merge.ff only`, under which a plain merge of the second parallel ticket fails with "Not possible to fast-forward"), resolve conflicts there without changing behavior beyond the resolution, and never touch another worktree. The merger is the only writer of the integration worktree and never runs the exact `checkCommand`. Its reply ends with exactly one verdict line: `MERGED <merge-commit-sha>`, `RESET <pre-merge-sha>` (it could not land a clean merge and restored the pre-merge SHA under the guards below), or `CONFLICT <detail>`.
2. Merger `MERGED <sha>` → state `POST_MERGE_CHECK`: run the exact `checkCommand` in the integration worktree at the merge commit — tree clean, HEAD matching the reported SHA. Record command, exit status, timestamp, HEAD, output pointer. Green → set `lastGreenIntegrationSha` to the merge commit SHA, resolve the ticket the way the tracker closes work (`gh issue close <n> --comment` naming branch, merge SHA, and the evidence pointer; closing is what unblocks dependents natively), terminal `PASSED`, take the next queue head.
3. Merger `RESET <sha>` (verify the reported SHA equals the recorded pre-merge SHA) or a failing post-merge check → undo before anything else merges: with no merger live, in the integration worktree verify the checked-out branch is the integration branch and the pre-merge SHA is an ancestor of HEAD, then `git reset --hard <pre-merge-sha>` (`git merge --abort` first if a merge is half-done), so the integration branch again equals `lastGreenIntegrationSha` and stays green. The ticket returns to the fix loop (step 8) with the integration-check output (or conflict) pointer and counts in the shared failed-pass budget; it re-enters the review gates from standards and the queue afterwards. Other queued tickets are never blocked by it — they merge next, in order.
4. Merger `CONFLICT <detail>`, or a malformed, missing, or `HANDOVER` merger verdict → the executor performs the guarded reset of step 3 itself, then re-runs the merger once with the same task body. A second bad verdict of any of those three classes (`CONFLICT`, malformed or missing, `HANDOVER`) → guarded reset to the pre-merge SHA, then exactly one counted fix-loop pass for that ticket (conflict or verdict pointer), after which it re-enters the gates and the queue. Never a third merger run for one merge attempt and never a stalled queue: the next queue head merges right after the reset. Merger `BLOCKED` → guarded reset, ticket `BLOCKED`; `ESCALATE` → guarded reset, `ESCALATED`.
5. Reset-guard failure — the guard verification does not hold or the `git reset --hard` itself fails → do not reset; repair from a temporary worktree at `lastGreenIntegrationSha` (`git worktree add <tmp> <lastGreenIntegrationSha>`, force the integration branch to `lastGreenIntegrationSha` via `git update-ref refs/heads/<integration-branch> <lastGreenIntegrationSha>`, remove and re-create the integration worktree on it) and record the repair in the state file. If the repair also fails, the run ends `ESCALATED` with the report naming the observed SHAs.
6. After every merge outcome, recompute the frontier from the tracker (Frontier section) and spawn implementers for newly unblocked tickets up to the width cap.

## Closing steps (once, then stop)

When the frontier candidate set is empty (a `SPLIT_WAITING` origin whose SPLIT child has closed is a candidate, so it keeps the set non-empty until respawned and terminal; one still blocked by a non-agent blocker, for example a SPLIT child that was handed off, is a leftover, below), no child is running, and the merge queue is empty — and `closingStepsDone` in `state.json` is false — perform the closing steps exactly once. Which turn triggers closing depends on who watches the run:

- **Watchdog-managed run** (the drain-watchdog extension is armed on the main session): the watchdog reads `closingStepsDone` from `/tmp/executor/<repo-slug>/<target>/state.json` every tick (repo slug = the lowercased repo directory name, non-alphanumeric characters collapsed to one dash, with no leading or trailing dash — the same value the path above uses). When the frontier empties it sends exactly one FINALIZING nudge ("drain-watchdog: frontier is empty. Finish the closing steps …"); react to that nudge by running this closing section now. Finishing means setting `closingStepsDone: true` in `state.json` and then calling `watchdog_done`: the watchdog re-reads the queue and the flag and completes the run as DONE at once, without waiting for idle time (its next tick would also complete it). Do not wait for a second nudge — if the run goes idle again with `closingStepsDone` still false, the watchdog pauses the run visibly ("finalization not confirmed") instead of nudging again.
- **Standalone run** (no watchdog armed): your own empty-frontier observation, evaluated in your active turn, is the closing trigger; run this section in that turn. The harness ends the run by reaching DONE from the empty, non-inflight queue.

In both modes the closing steps run exactly once, guarded by `closingStepsDone` (false until they have run). `watchdog_stop` only pauses a run and is never used to complete one — completion is `watchdog_done` (watchdog-managed run), which the watchdog verifies and refuses while anything is left. Steps:

1. Frontier-empty remainder: open target tickets still blocked by non-agent tickets — non-agent = a blocker lacking `ready-for-agent` — or by `needs-info` / `ready-for-human` / `wontfix` labels are listed as leftovers with their blockers, read live per ticket: `gh api repos/{owner}/{repo}/issues/<n>/dependencies/blocked_by --jq '.[] | select(.state=="open") | {number,state,labels}'`. Reported, never nudged, never worked.
2. Confirm the integration tip equals `lastGreenIntegrationSha`. If it does not, never adopt it unchecked: run the exact `checkCommand` on the tip once; green → update `lastGreenIntegrationSha`; red → the guarded reset to `lastGreenIntegrationSha` (merge loop step 3), the ticket whose merge produced the tip returns to the fix loop (counted) and the run goes back to the frontier instead of closing — closing resumes only once the tip equals `lastGreenIntegrationSha`.
3. `closing: pr` → push with the explicit refspec `git -C <integration-worktree> push -u origin integration/<slug>:integration/<slug>`, then open a ready (not draft) PR with `gh pr create --base <default-branch> --head integration/<slug>` whose body lists merged tickets, check evidence, and leftovers — idempotent: `gh pr list --head integration/<slug>` first and reuse or update an existing PR instead of duplicating it. The executor never pushes to `<default-branch>` and never runs a bare `git push` (under `push.default=upstream` a bare or branch-only push can land on the upstream branch). `closing: branch` → no push, report the branch and tip SHA.
4. Clean up in this order: (i) remove the worktree of every `PASSED` ticket (`git worktree remove <path>`, never forced; git refuses to delete a branch still checked out in a worktree); (ii) delete each merged ticket branch from inside the integration worktree with `git -C <integration-worktree> branch -d <branch>` (from the main checkout `branch -d` may refuse or only warn, because the work lives only in the unpushed integration branch); (iii) remove the integration worktree last. A refusal or an already-removed path or branch is recorded and treated as done (kept, listed). Keep worktrees and branches of unmerged tickets (`FAILED`, `BLOCKED`, `SPLIT_WAITING`, `ESCALATED`) as partial-work pointers and list them. The integration branch is kept.
5. Persist `closingStepsDone: true`, then post the run terminal. Never call `watchdog_stop` to complete: it only pauses. In a watchdog-managed run call `watchdog_done` last.

## Terminals

Per ticket — exactly one, commented on the ticket with the pass report pointer: `PASSED` = standards PASS + green check + spec PASS + merged into the integration branch with a green post-merge check; `FAILED` = failed-pass budget exhausted; `BLOCKED` = refused input, implementer or merger `BLOCKED`, an implementer or reviewer malformed or missing verdict (a merger's is recoverable under merge loop step 4, never a terminal by itself), depth-cap or no-smaller-scope split refusal, or handoff (a successful split's origin is the `SPLIT_WAITING` non-terminal above, not this `BLOCKED`); `ESCALATED` = a child reported `ESCALATE`; never reroute, never retry. No terminal leaves the ticket open, `ready-for-agent`, and assigned: `PASSED` closes the ticket with the evidence comment; `FAILED` and `ESCALATED` relabel it `ready-for-human`, post the evidence or reason comment, and free the claim; `BLOCKED` takes the label its cause maps to (`docs/agents/triage-labels.md`): `needs-info` only when information is missing from the human (refused, contradictory, or ambiguous input, or an implementer `BLOCKED` whose report names missing information), `ready-for-human` whenever a human action or decision is required (low-tolerance handoff, split-depth cap, no strictly smaller scope, merger `BLOCKED`, an implementer or reviewer malformed or missing verdict, any other implementer `BLOCKED`); it comments the reason and frees the claim. Every relabel above and in the handoff paths is one edit that also removes `ready-for-agent`: `gh issue edit <n> --remove-label ready-for-agent --add-label <label> --remove-assignee @me`. So no terminal ticket can re-enter the frontier or count as in flight.

Run — one final reply once closing is done or the run cannot continue; any `ESCALATED` ticket → `ESCALATED`, else any `BLOCKED` → `BLOCKED`, else any `FAILED` → `FAILED`, else `PASSED`. Leave `<default-branch>` untouched and the tree clean:
`VERDICT: PASSED | FAILED | BLOCKED | ESCALATED`
`SUMMARY: <one sentence>`
`TARGET: #<n>; INTEGRATION: <branch>@<lastGreenIntegrationSha>; STATE: <state.json path>; PR: <url|none>`
`TICKETS: passed=<list>; failed=<list>; blocked=<list with reasons>; escalated=<list>; leftover=<list with blockers>`
`ATTRIBUTES: failedPasses=<n>; handovers=<n>; splits=<n>; merges=<n>; mergeReverts=<n>; standardsReviews=<n>; specReviews=<n>`
