# Declarative Pi Home Manager configuration

## Problem Statement

Pi currently combines portable configuration with machine-local runtime state under `~/.pi/agent`. Configuration is not reproducibly synchronized across machines, while an earlier Bun installation accidentally supplied modules needed by user-installed plugins. After that installation was removed, `@juicesharp/rpiv-ask-user-question` could no longer resolve `@earendil-works/pi-tui` from Nix-packaged Pi.

The owner needs one public, commit-pinnable Home Manager module that preserves Pi's native behavior, keeps secrets and runtime state local, packages plugins with complete immutable dependency closures, and stays current through checked updates.

## Solution

Export a Home Manager module as `homeManagerModules.default`. Importing it enables Home Manager's native `programs.pi-coding-agent` module through `lib.mkDefault true`, selects Pi from this repository's pinned `nixpkgs-unstable`, applies audited portable defaults, links only resources Home Manager does not already support, and supplies Nix-built plugins as immutable local package paths through Pi's native `settings.packages` mechanism.

The module adds one option only: `programs.pi-coding-agent.apiKeyFiles.<provider>`. It converts each runtime secret-file path into Pi's native shell-command key resolution without placing secret content in Git or the Nix store.

One daily GitHub Actions workflow updates pinned `nixpkgs` and Home Manager together, checks the result, then independently updates each registered plugin. Consumers remain reproducible because they pin a commit of this repository and advance it deliberately.

## Implementation Decisions

### Flake and module surface

- Inputs are `nixpkgs-unstable` and Home Manager; Home Manager follows the pinned nixpkgs.
- Outputs are limited to `homeManagerModules.default`, `checks.x86_64-linux`, and `formatter`.
- Formatter is nixpkgs `nixfmt`; no treefmt framework or development shell is added.
- The module requires the exact minimum Home Manager commit documented in README, or newer, containing `programs.pi-coding-agent`.
- The repository pins Home Manager for its checks but does not import a second pinned copy into a consumer's module graph.
- `programs.pi-coding-agent.enable` and `package` are assigned with `lib.mkDefault`.
- Default package is `pi-coding-agent` from this repository's pinned nixpkgs.
- Consumer package overrides are allowed, but managed plugin compatibility is guaranteed only for the default package.
- All module effects are guarded by the final Pi enable value.

### Home Manager ownership

- Home Manager's built-in Pi options exclusively own settings, keybindings, models, global context, package installation, and any other paths it supports.
- This module does not recreate or separately link a path already owned by Home Manager.
- Unsupported, repo-owned resources mirror their native Pi layout under `pi/` and are linked immutably with `home.file`.
- No resource enable flags, per-resource options, writable copies, or raw-resource templating are added.
- The module exclusively owns `programs.pi-coding-agent.settings.packages`; consumers may specialize other settings but do not merge package entries.
- Nix-generated user paths use `config.home.homeDirectory`.

### Managed and runtime boundaries

- Migration uses an explicit managed-path allowlist. Unknown paths are excluded.
- Portable homeserver values become common defaults only after auditing secrets, absolute paths, and machine coupling.
- Authentication, sessions, logs, caches, crash data, trust data, goals/state, generated npm/git trees, and other mutable state remain machine-local.
- Home Manager consumer configuration owns conflict backup and activation policy.
- Claude Code migration remains out of scope until Pi work is accepted.

### Runtime secret API

Model API keys use this custom option:

```nix
programs.pi-coding-agent.apiKeyFiles.<provider> = <runtime-path>;
```

For each key, the module:

- requires a matching `programs.pi-coding-agent.models.providers.<provider>`;
- rejects a provider that also defines `apiKey`;
- shell-escapes the runtime path;
- merges `apiKey = "!cat <escaped-path>"` into the native models option;
- never reads secret content during evaluation or activation.

The importing configuration provisions and permissions the runtime file. The API does not mention sops-nix, agenix, or another secret manager.

### User-level MCP configuration

<Decision title="Reuse Home Manager's MCP registry and runtime secret wrappers" status="accepted">

`programs.mcp.servers` is the single user-level MCP server registry. Pi exposes only `programs.pi-coding-agent.plugins.pi-mcp-adapter.enableMcpIntegration` and adapter-specific `settings`; it does not define a second server schema.

The integration renders enabled user servers into `${programs.pi-coding-agent.configDir}/mcp.json`. Local stdio servers with `env.<name>.file` use Home Manager's `lib.hm.mcp.wrapEnvFilesCommand`: generated JSON contains an immutable wrapper path, while the wrapper reads the runtime file and exports its content only to the MCP child process. Secret content never enters evaluation, generated JSON, the Nix store, or Pi's environment.

The module owns no repository-level `.mcp.json` or `.pi/mcp.json`. `pi-mcp-adapter` may still discover those files at runtime by upstream behavior. File-backed remote HTTP headers are deferred because Home Manager's native wrapper supports only local stdio environment variables; do not use `builtins.readFile` as a substitute.

</Decision>

### Plugin registry

`pi-plugins.json` is an object keyed by stable aliases. Each entry resembles derivation metadata:

- common: `pname`, `version`, protocol-prefixed `src`, `hash`, `npmDepsHash`;
- git only: manually reviewed branch `track` and exact resolved `rev`;
- git version: updater-generated `unstable-YYYY-MM-DD`;
- npm version: exact registry version, never a range.

`src` contains source identity but not version or revision. Registry additions, removals, aliases, source changes, and tracked-branch changes require manual review. Automation may only update npm versions or resolve the configured git branch head, then refresh hashes.

Registry v1 deliberately omits package resource filters and `autoload`. Pi supports `extensions`, `skills`, `prompts`, and `themes` filters, where omission loads all and `[]` disables a type; `autoload: false` supports global/project deltas. Add those fields together only when a concrete selective-loading need appears.

### Plugin and local-extension packaging

- One standard npm-oriented Nix builder handles both registry packages and local extensions.
- Each output contains its third-party runtime dependency closure. Pi core packages remain declared peers, are supplied by Pi's package loader, and must pass an offline load smoke test against the pinned Pi package.
- No user-level npm installation, shared extension dependency bundle, or ad hoc import from Pi's Nix-store internals is permitted.
- Each local extension lives in its own directory with adjacent source and dependency manifest/lock metadata.
- No speculative builder override field exists in registry v1. If audit proves a package needs an exception, add the smallest concrete field then.
- Built plugin closures are passed as immutable local paths through native Pi `settings.packages`.
- Local extensions live in the repository rather than `pi-plugins.json`.

<Decision title="Set up project-local sequential ticket drain agents" status="accepted">

Drain roles are repository-local machine policy, not universal user policy and not shared repository content. `/drain-wizard` creates machine-local definitions under the trusted repository's canonical `.pi/agents/drain/` scope only when discovery finds missing/drifted agents or the user requests agent edits. This keeps drain mechanics private to each clone/machine and avoids changing shared repository policy. ### Machine-local drain contract

Use the existing `huly-loop-contract.json` and `HULY-LOOP-PROMPT.md` from `ms-sbn` as behavioral evidence, not files to copy verbatim. They contain useful validation, exact-state, route, dependency, ordering, URL-template, and idempotency lessons, but are coupled to Huly, GitLab, Telegram, systemd, branch deployment, and one employee identity. The generic setup must not import those private values or its monolithic runtime prompt.

`/drain-wizard` also creates `.pi/drain/contract.json` from a managed versioned schema and excludes `.pi/drain/` through the same clone-local Git exclude. The contract is the single runtime source of truth; prompts and agent definitions must not restate provider ids, state names, budgets, report paths, branch targets, or routing rules.

Minimum contract sections:

| Section | Required contents |
|---|---|
| `schemaVersion` | Exact supported integer; unknown versions and unknown keys fail closed. |
| `repository` | Resolved Git common directory identity, remote, base branch, delivery branch pattern, PR target, exact check commands as argument arrays, coding-standards path, report root, and accepted UI evidence roots. |
| `ticketPool` | One provider per clone; provider kind (`github` or `huly` initially), existing auth/tool reference without credentials, workspace/repository and project ids, ticket URL template, ready filter, dependency relation, deterministic ordering, and claim selector. |
| `ticketStates` | Provider-native selectors and transitions for `ready`, `claimed`, `review`, `readyForHuman`, and `done`; use immutable ids when the provider exposes them, otherwise exact repository-scoped names. State plus required labels must uniquely identify each phase. |
| `housekeeping` | Continuous bounded-round cadence, review-ticket selector, completion gate (`merge` or `deployment`), MR provider, exact deployment environment/trigger, terminal pipeline selectors, optional notifier/destination plus reminder cadence, and failure outcome. |
| `routing` | Changed-path rules for UI, UX, database, and low-tolerance review. Overlapping rules accumulate reviewers; they never remove a mandatory gate. |
| `budgets` | `quick: 5` and `deep: 3`; setup may lower them but cannot disable a mandatory review. |
| `ownership` | Machine/clone marker used for comments and claims, plus explicit `claimBeforeSpawn: true`. No secret values. |
| `telemetry` | Local audit path, configured OTel endpoint reference if present, and redaction policy reference. |

V2 supports exactly one ticket pool and one housekeeping policy per clone, plus ordered hotfix and normal delivery lanes. Delivery ends at opened PR; fresh bounded `housekeeper` rounds reconcile asynchronous MR and build-deployment state throughout the same drain invocation and on later invocations. Auto-merge remains forbidden. Auto-deploy is allowed only for an environment proven to be development or staging; production, production-like, protected-production, and unknown environments are human-only. Hotfixes never bypass review.

Setup runs a fail-closed Doctor before writing agents:

1. detect supported ticket provider and existing authenticated tool;
2. let the user select the ticket pool, then resolve project, states, labels, assignee, and dependency relation to stable ids;
3. verify branches, remote, standards, checks, report/UI paths, and provider read/write capabilities;
4. reject ambiguous states, overlapping claim ownership, missing placeholders, embedded credentials, shell-string checks, or route combinations that can silently skip review;
5. preview generated files and contract, write only after approval, then perform a read-only candidate query and live agent-discovery smoke test.

Only `delivery-orchestrator`, `housekeeper`, and the invoking main agent may mutate tracker state, comments, labels, or PR/deployment links; only delivery claims ready tickets. Builders and reviewers receive immutable ticket snapshots and return strict verdict/report pointers. This improves the reference Huly design, where implementers and reviewers also mutate tracker state and duplicate notification obligations.

At each drain start, validate the contract again, hash it into the audit record, acquire the Git-common-directory singleton, query one candidate, re-read eligibility immediately before claim, claim remotely, then spawn delivery. Invalid contract, ambiguous remote ids, lost claim, or provider failure makes zero source changes and stops. If delivery dies after claim, the surviving parent—or the next preflight detecting its stale machine claim—moves the ticket to `readyForHuman` with available report pointers; no branch-based crash resume.

### Drain telemetry

Use Pi/subagent runtime tracing rather than a new daemon or backend. One trace covers a drain invocation; child spans cover housekeeping reconciliation, MR lookup, deployment trigger/watch, provider query/claim, ticket delivery, checks, each review gate, PR creation, and terminal transition. Propagate trace context into subagent prompts and reports. Structured local audit events record contract hash, state transition, verdict, report pointer, duration, and trace id; ticket bodies, comments, diffs, credentials, and report contents are excluded.

Metrics use low-cardinality labels only: provider, gate, verdict, and error kind. Emit ticket outcome and review-round counters, active-delivery gauge, provider-call latency histogram `[10, 50, 100, 250, 500, 1000, 2500, 5000, 10000]` ms, and delivery-duration histogram `[1, 10, 60, 300, 900, 1800, 3600, 7200]` seconds. Ticket/project/user ids stay on sampled spans, never metric labels. Auth tokens and headers are Tier A `<redacted>`; no ticket free text enters telemetry. Setup reuses an existing OTLP configuration when present and otherwise keeps the local audit without installing a collector.

### Producer-reviewer separation

The `build-lead` instance that creates a diff never sees, selects, spawns, steers, or communicates with its reviewers. `delivery-orchestrator` spawns every reviewer as a fresh sibling using ticket/spec, standards, commit SHA, check evidence, accepted UI artifacts, and the actual diff—not the producer's explanation. On rejection, the producer ends permanently; delivery passes the opaque findings pointer to a fresh `build-lead`, then fresh reviewers inspect the revised commit.

```text
Lead A creates commit
  → delivery runs checks
  → delivery spawns sibling reviewers
  → reviewer rejects
  → Lead A ends permanently
  → delivery spawns Lead B with findings pointer
  → fresh sibling reviewers inspect Lead B
```

Review routing belongs to delivery. UI changes add `ui-reviewer` to the quick gate and `ux-reviewer` to the deep gate. Database changes add the database-performance axis to `quick-reviewer`. Changed-path metadata should drive these conditions; the producer does not self-certify which reviews it needs.

### Sequential drain state machine

Exactly one drain orchestrator may run per Git common directory per machine, and it consumes exactly one ticket at a time. At invocation start, main starts one fresh bounded `housekeeper` as a non-blocking sibling and rotates fresh rounds while sequential ready-ticket delivery continues, then performs a final scan before idle. Ticket-level work is sequential; `build-lead` may still fan out disjoint work inside that ticket. The tracker is durable workflow state: drain queries one open `ready-for-agent` ticket whose blockers are closed, claims it before spawning, and queries the tracker again only after successful delivery. An opened PR completes delivery for that ticket, so another independent ticket may run; dependent tickets remain unavailable until housekeeping verifies the configured merge/deployment completion gate and moves the blocker ticket to `done`.

Review counters are local to one `delivery-orchestrator` invocation and need no persisted resume state:

- quick gate budget: five rounds, each consisting of the exact check, `quick-reviewer`, and conditional `ui-reviewer`;
- deep gate budget: three rounds, each consisting of `deep-reviewer` and conditional `ux-reviewer`.

A quick-gate rejection spawns a fresh lead and returns to the quick gate. A deep-gate rejection also spawns a fresh lead and restarts at the quick gate because the revision may break checks, standards, or visual fidelity. The originating lead never receives findings. Every spawn returns a strict verdict and report reference; malformed output fails closed.

```text
ready-for-agent
  → claimed
  → fresh build-lead
  → quick gate (max 5)
  → deep gate (max 3)
  → PR opened
  → query next independent runnable ticket

quick/deep budget exhausted | blocked | escalated | delivery crash
  → note-taker
  → NEEDS_HUMAN + worklog/report pointers
  → main removes ready-for-agent and marks ready-for-human
  → issue stays open, so dependents remain blocked
```

Housekeeping scopes candidates by project/repository, configured review selector, drain ownership marker, and drain-authored PR reference; it never sweeps a shared team column by status alone. Open MR stays pending and may produce an idempotent reminder only when notifications are configured and due. Closed-unmerged, missing/inconsistent evidence, terminal failed/cancelled/timed-out deployment, or trigger failure moves the ticket to `readyForHuman` with evidence pointer. Merged MR completes immediately only when `completionGate` is `merge`. For `deployment`, housekeeper first finds a deployment for the exact merged SHA; green moves ticket to `done`, running is watched to terminal, and absent deployment is triggered only when `autoDeploy` is true, current invocation carries outward-action approval, and provider/CI evidence proves the target is development or staging. It never auto-merges, promotes to production, retries failed code, or duplicates a trigger already identifiable by SHA/marker.

A ticket marked `ready-for-human` is never consumed again. Human re-adding `ready-for-agent` is explicit retry authorization and starts a new delivery with fresh local budgets. Local singleton enforcement does not replace the remote tracker claim if multiple machines may drain the same repository.

The terminal delivery contract is pointer-only:

```text
VERDICT: PASS|REVISE|BLOCKED|ESCALATE|NEEDS_HUMAN
TICKET_REF: <issue>
REPORT_REF: <path>
PR_REF: <url-or-none>
ATTRIBUTES: ui_touched=<bool>; db_touched=<bool>; build_attempts=<n>; quick_attempts=<n>; deep_attempts=<n>
```

For UX errors, choose the first available correlation value in this order: `X-Response-ID`, `X-Request-ID`, `X-Trace-ID`, then the trace id extracted from `traceparent`. If none exists, show only the user-safe message. Never expose a raw system error; an expected shape is `5WQDT: Gagal mengambil data dari server`. Cross-origin responses must expose any readable correlation headers.

</Decision>

<Decision title="Use wizard-generated brownfield drain contracts" status="accepted">

This decision supersedes conflicting contract, resume, counter, ticket-outcome, and queue-stop details in the preceding drain decision.

`/drain-wizard` is the sole setup/edit surface. It inspects current tracker/SCM state, interviews one section at a time, reuses brownfield constructs, offers only missing roles/markers, previews remote additions, and writes machine-local `.pi/drain/contract.json` plus provider/policy-specific `.pi/drain/DRAIN-PROMPT.md`. The generated prompt is SHA-256-bound to its sibling contract. `/drain <path-to-DRAIN-PROMPT.md>` is a thin validated loader. `pi-prompt-template-model` is retained; prompt-authoring commands inject `writing-great-skills` through frontmatter.

Contract roles are semantic rather than canonical tracker names: `ready`, `inProgress`, `review`, `needsHumanReview`, and `done`. Every configured project maps these roles and one authoritative ticket work-contract source to existing statuses, fields, labels, comments, or linked specs. Multiple tracker projects may feed one repository; operator guarantees they belong to one vertical product. Human comments remain task context, while structured drain comments are control data rather than task instructions.

Runtime state is an append-only ledger of schema-valid tracker comments. Events persist owner, contract hash, lane, phase, branch/revision, report/MR/deployment refs, and build/quick/deep/deploy-fix counters. A ledger fork fails to `needsHumanReview`. Human requeue to mapped `ready` starts a new generation and resets counters.

Selection re-queries tracker after every ticket and uses this fixed order:

```text
oldest resumable inProgress
  → oldest ticket matching first hotfixPolicies[] entry
  → oldest ticket matching first policies[] entry
  → settle housekeeping, final scan, then stop until external ticker
```

Every ticket outcome—PASS, failure, exhaustion, ambiguous, or L/XL—persists its terminal event and continues to next-best ticket. `build-lead` returns `NEEDS_HUMAN_REVIEW` before implementation for ambiguous or L/XL scope; delivery/main performs tracker mutation. Resume requires same owner, valid ledger, and branch ref, and continues persisted budgets.

`hotfixPolicies[]` is a separate tier, not a kind inside normal `policies[]`. Hotfix uses production source, full review, reviewed cherry-pick to a development/staging validation branch, deployment babysitting, then one upstream MR per ticket to production after green. Normal lanes open one active MR per ticket; a code-caused post-merge deployment failure may open a follow-up fix MR. Fresh `deep-reviewer` classifies deployment failure: infrastructure/ambiguous → `needsHumanReview`; code → fresh lead plus all review gates. Deploy-fix budget is two.

Housekeeper reconciles async MR/deployment state through rotating bounded rounds in the active drain and again on each external tick, opens the hotfix upstream MR after non-production green, and updates mapped ticket roles idempotently. `autoDeploy` is durable authorization only for an exact development or staging environment/trigger. Production, production-like, protected-production, unknown environments, auto-merge, and staging-to-production promotion remain human actions.

</Decision>

<Decision title="Rotate bounded housekeeping throughout one drain session" status="accepted">

This decision supersedes the original external-tick-only housekeeping cadence. Contract schema advances to v2; append-only ticket state events remain v1 because reminder timing is clone-local operational state. Existing machine-local v1 contracts must be regenerated through `/drain-wizard` rather than guessed forward.

Main keeps at most one asynchronous housekeeper and one asynchronous ticket delivery active. It waits for whichever sibling settles, preserving sequential tickets while allowing housekeeping rotation during long delivery. Each fresh bounded round scans drain-owned review tickets, synchronizes MR/PR and ticket roles, refreshes build/deployment status at configured cadence, then terminates at its round deadline. Main validates the result and rotates another fresh sibling while the drain remains active. Settle stops rotation, waits for the current round, runs one final scan-only round, processes all outcomes, and re-runs ticket selection once. MRs opened later in the same invocation therefore enter housekeeping without one immortal watcher or a separate daemon.

Housekeeping configuration is per repository: `pollSeconds` defaults to 60, `roundWindowSeconds` to 900, and `maxTicketsPerRound` bounds load. Notifications remain optional. `notifications: null` means sync plus local audit only. When configured, wizard must resolve an installed notifier and destination without embedding credentials; `remindAfterSeconds` defaults to 7200 and `repeatEverySeconds` to 86400. Reminders cover only `merge-request-open` and `build-running`. Clone-local audit persists reference, first observation, last notification, and reminder count. First observation uses trustworthy provider state-entry time when available, otherwise local first-seen time; ticket generation + ref + observed state + due window forms an idempotency key. Ref/state changes reset the clock. Notification failure is audited but never changes ticket state or blocks reconciliation.

Existing safety stays fixed: no auto-merge, no production deploy/promotion, exact-SHA deployment lookup before trigger, and failure classification before `needsHumanReview`. Reminder payload contains ticket/MR/build refs and bounded state only—no ticket/comment text, credentials, headers, or report contents.

Telemetry reuses the existing drain trace and local audit. Add child spans for housekeeping round, MR/build refresh, and notifier call; record round lifecycle, reminder due/dedupe decision, notification result, duration, and trace id. No new daemon, collector, metric family, or high-cardinality metric label.

### Daily update workflow

- Schedule: daily at `03:00 UTC` and parameterless `workflow_dispatch`.
- Permission: built-in `GITHUB_TOKEN` with `contents: write`; no PAT, deploy key, or GitHub App.
- Input job updates pinned nixpkgs and Home Manager together, runs full x86_64-linux checks with current plugins, and creates one commit only when changed.
- Plugin job uses `if: always()` and a fresh checkout of latest `origin/main`.
- One serialized shell loop processes aliases independently, resetting failed changes before continuing.
- Each changed plugin gets its own check and conventional commit.
- A failed input update does not block plugin updates against last valid `main`.
- A failed plugin does not block later plugins; plugin job reports aggregate failure after processing all aliases.
- Before each push, automation fetches and rebases current `main`; relevant upstream changes rerun the target check.
- One bounded retry handles a concurrent update. Automation never force-pushes.
- No-op updates write summary status but create no commit.
- Commit subjects use `chore(deps): update nixpkgs and home-manager` and `chore(pi-plugins): update <alias> to <version>`.

Home Manager owns `pi-vcc-config.json` and exports `PI_VCC_CONFIG_PATH`, so custom Pi config directories remain correct and extension scaffolding becomes a no-op. `vcc_recall` reads the active session JSONL and exposes off-lineage content only through explicit `scope: "all"`. </Decision>

<Decision title="Use Nix Chromium for pi-playwright" status="accepted">

`pi-playwright` keeps its npm-declared CLI range in an adjacent lock file. </Decision>

<Decision title="Resolve pi-subagents peers from host Pi" status="accepted">

`pi-subagents` bundles `jiti`, `yaml`, and runner-loaded `typebox`, removes test-only Pi copies, and keeps its optional Pi peer declarations. Offline loading and structured-output validation against the managed Pi package verify compatibility without duplicating the host Pi runtime closure.

</Decision>

## Out of Scope

- Claude Code migration or configuration; it starts after Pi acceptance.
- Machine profiles such as homeserver, boxes, or home desktop.
- nix-darwin validation; Darwin is only design-primed.
- `aarch64-linux` release-gate checks in this phase.
- Secret storage, encryption, decryption, or secret-manager configuration.
- Home Manager conflict backup or activation deployment policy.
- Runtime mutation through `pi install`, `pi update --extensions`, npm, or git package directories.
- Package resource filters and `autoload` in registry v1.
- Behavior-level tests for every third-party plugin.
- Malware detection or manual review of every automated plugin release.
- Automatic local-extension dependency updates.
- OpenTelemetry, external notifications, dashboards, or report artifacts.
- Ready-made `homeConfigurations`, NixOS modules, machine-specific options, or broad custom option surfaces.

## Further Notes

- Automated plugin updates execute third-party code after build and load-only validation. This risk is accepted. Consumer commit pins contain rollout, and reverting the pin is rollback; neither mechanism detects malicious releases.
- Pi's native package protocol supports npm, git, URL, and local path sources. Registry v1 packages npm and git sources into local immutable paths before Pi sees them.
- The exact nixpkgs npm build primitive, Nix function signatures, package availability, current Home Manager minimum commit, and formatter command must be confirmed through configured NixOS/Noogle MCP servers or upstream documentation during implementation.
- Issue-tracker publication is not performed in this planning pass because no issue tracker or `ready-for-agent` label configuration exists in the repository.
